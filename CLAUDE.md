# TV News Reader

A news reader for the TV, used only with the remote. Users browse stories by category, read articles and save stories for later. Requirements come from the project checklist "Project: TV News Reader" (39 items in 7 sections). An item counts as done only when it works on **both** targets, tested on a real TV where possible.

## Targets

| Target | How it runs | Oldest supported |
|---|---|---|
| Android TV | Native app (React Native, react-native-tvos) | — |
| LG webOS | Web build (react-native-web + webpack), packaged as `.ipk` | **webOS 22 = Chromium 87** |

There is no Samsung Tizen and no Apple TV target, so there is no `ios/` folder.

## Stack

- **React Native CLI + TypeScript.** `react-native` is aliased to `react-native-tvos@0.83.0-0` in `package.json`, which adds TV focus and remote support (`hasTVPreferredFocus`, `useTVEventHandler`, `TVFocusGuideView`).
- **Web:** `react-native-web` renders the same components as HTML. Webpack bundles them (`webpack.config.js`).
- **Navigation:** React Navigation 7 native stack (`@react-navigation/native-stack` + `react-native-screens`), set up in `App.tsx`, no header, no animation. Every screen is wrapped in `ErrorBoundary` via `screenLayout`, so a crash shows an error state with "Try again" instead of killing the app; wrap risky parts inside a screen (e.g. each Home row) in their own `ErrorBoundary` too. Screens and their params are listed in `src/types/navigation.ts`; screens type their props as `ScreenProps<'Name'>`. No `linking` config, so it never touches browser history (webOS has it turned off). Webpack needs `resolve.fullySpecified: false` for its `.js` files, and Jest's `transformIgnorePatterns` must include `@react-navigation` and `react-native-screens`.
- **Babel:** Android uses `babel.config.js` (Metro). The web build ignores that file and sets its own Babel options inside `webpack.config.js` (it also converts class fields, so the bundle passes the ES2021 check). Keep the `@babel/*` packages on **version 7**, because React Native needs Babel 7.

## Commands

| Goal | Command |
|---|---|
| Develop in a desktop browser | `npm run web`, then open http://localhost:8080 |
| Run on Android TV (emulator or `adb connect <ip>:5555`) | `npm start` + `npm run android` |
| Build web only | `npm run build:web` (output in `dist/`; fails if the bundle uses syntax newer than ES2021, the newest level Chromium 87 fully supports) |
| Build, package, install and launch on LG TV | `npm run webos` |
| Debug on LG TV (Chrome DevTools) | `npm run webos:debug` |
| Type check / tests / lint | `npm run typecheck` / `npm test` / `npm run lint` |
| Format code (project Prettier style, e.g. `import { View }` with spaces) | `npx prettier --write "src/**/*.{ts,tsx}"` |

**LG TV setup (once per TV):** install the Developer Mode app on the TV and turn it on, then run `ares-setup-device` (name `tv`, port 9922, user `prisoner`) and `ares-novacom --device tv --getkey`.

**Component-based structure.** Screens in `src/screens/<Name>Screen/` only arrange components and import them from `../../components/<Name>/<Name>`; a screen folder holds the screen and its own files (e.g. `HomeScreen.styles.ts`). Every component is a folder in `src/components/` with `Name.tsx` (named export), `Name.styles.ts` and `Name.types.ts`. There are no `index.ts` files: always import the file itself, never a folder. A component's sub-components go in a `components/` folder inside it, at any depth (e.g. `SearchKeyboard/components/Key/`), and only that parent imports them. Components used by more than one screen go in `src/components/shared/`. Every main screen (Home, Category, Search, Saved, Settings) wraps its content in `MainLayout current="..."` so the menu bar is always reachable, in every state; MainLayout's content area traps Left/Right, so the menu is only reached with Up (otherwise a Right press near the top can score a menu item as nearest); Article stays full screen. Menu navigation: from Home it pushes the section, between sections it replaces, and Home pops back, so Back from any section returns to Home and then to the exit dialog.

**Hooks vs utils.** A hook is a function that calls other React hooks; it lives alone in `hooks/<useName>/<useName>.ts`, wherever it is used (theme and language hooks included). A util is plain logic that calls no hooks; it lives in `utils/<name>/<name>.ts`. `api/` keeps only code that fetches or stores data, `theme/theme.ts` keeps the design values (`createTheme`, `colors`, `Theme`). Plain functions, even ones only a hook uses, go in `utils/<name>/<name>.ts`. Anything that renders (returns JSX) is a component in `components/`, never a util or part of a hook; a component's React context goes next to it as `Name.context.ts`.

**Types.** Types used in more than one place go in `src/types/`. Each component's own props go in `Name.types.ts` in its folder (shared components too), and the same for hooks (e.g. `hooks/useCenteredRail/useCenteredRail.types.ts`), written as an `interface` (e.g. `export interface FocusableButtonProps`); `Name.tsx` imports it. Components use the app's `Story`/`Article` types, never the raw `DevtoArticle`; only `api/devto.ts` touches that.

## Rules

1. **Keep platform differences in `src/platform/` only.** Write `name.ts` for Android and `name.web.ts` for webOS. Webpack picks `.web.ts` first and Metro picks `.ts`, so each module is a folder `platform/name/` holding `name.ts` and `name.web.ts`, and code imports `.../platform/name/name` (e.g. `platform/back/back`). Screens never check the platform themselves (checklist item 6.1).
2. **Web code must run on Chromium 87.** Babel and `core-js` handle JavaScript syntax and most missing functions. CSS features are not polyfilled, so don't rely on CSS `aspect-ratio` (added in Chrome 88), `:has()` or container queries. Use fixed sizes or the padding trick for image boxes.
3. **Back key:** listen only through `onBack(handler)` from `platform/back/back` (Android hardware Back; webOS key code `461`, since `appinfo.json` sets `disableBackHistoryAPI: true`; Escape in the desktop browser). The newest listener runs first; return `true` when handled. Register it in a `useEffect` and return its cleanup. App's listener goes back one screen, or on Home opens `ExitDialog` (focus starts on "Stay"; Back closes it, so a quick double Back never exits). Dialogs use RN `Modal` (traps focus on both targets) and also pass `onRequestClose`, which is how Android delivers Back to an open Modal.
4. **Styles live in their own file.** Each component has `Name.styles.ts` exporting `makeStyles = (theme: Theme) => StyleSheet.create({...})`, and `Name.tsx` calls `const styles = useStyles(makeStyles)` (from `hooks/useStyles/useStyles`). Styles never use raw colors or sizes; they take them from the theme. The screen width is read once at startup (`Dimensions.get` in `theme.ts`; a TV screen never resizes, so there is no live resize handling, and resizing the desktop browser needs a reload). The theme is rebuilt only when the language changes (`useLanguage`), which is why styles still go through `useStyles(makeStyles)`. Every `Text` style sets `fontFamily` from the theme, and `lineHeight` from `theme.lineHeight` next to its `fontSize`. Font: Android uses the system font (it covers Arabic). webOS uses the LG system font (`LG Smart UI`) first, with a bundled Noto Sans Arabic (`@fontsource/noto-sans-arabic`, Arabic letters only, see `platform/fonts/fonts.web.ts`) as fallback. Line heights matter because Arabic needs taller lines (1.6× vs 1.3×) or its letters get clipped. Use `theme.isRTL` only for things start/end can't flip, such as mirroring an arrow icon. Sizes are written in 1920x1080 design pixels; any size not already in the theme (e.g. a card width) goes through `theme.scale()`, so it fits 720p, 1080p and 4K and both Android (~960 wide) and webOS (1920 or 1280 wide). (These are React Native style objects, not CSS. react-native-web turns them into CSS on webOS.)
5. **Use logical styles** (`marginStart`/`marginEnd`, not left/right), so the Arabic right-to-left layout works.
6. **Focus: wrap every set of focusable items in `FocusGroup`** (`components/shared/FocusGroup`). `remember` returns focus to the last focused item when coming back (first item on the first visit); `trap={['left','right','up','down']}` stops focus leaving in those directions. Use `remember` + `trap={['left','right']}` for every horizontal row, and make it center-locked with `useCenteredRail` (`hooks/useCenteredRail`: pass the card width, gap and start padding, put `listRef`/`onLayout` on the FlatList and call `centerOn(index)` from each card's `onFocus`; focus moves until the card reaches the middle, then the row slides under it), and trap the sides of anything with nothing beside it (e.g. the top story). Android uses `TVFocusGuideView` (`autoFocus`, `trapFocus*`); webOS uses our arrow-key engine in `platform/spatialNavigation` (started once in App), which reads the same settings from `data-focus-*` attributes, only counts an item as being in the pressed direction if it is clearly there (by at least 25% of its size, so a focused card scaled up next to its neighbours never makes Up/Down pick a neighbour in the same row), leaves scrolling to the centering hooks (it only scrolls an item into view itself if it is still off-screen 250 ms after focusing), keeps focus inside open dialogs, and when focus is lost (Back from a screen, a dialog closing, an item disappearing) first moves it to an item that has just become preferred (`hasTVPreferredFocus` switched on, e.g. the row that takes a removed row's place), otherwise returns it to the most recently focused item that is still visible, falling back to the first item. This is how webOS matches Android, which restores focus natively. On Android `FocusGroup` is a `TVFocusGuideView`, and a `flex: 1` child inside it collapses to 1 px; give such children (e.g. a FlatList) `height: '100%'` and the group itself a definite height. To debug focus on Android, log in `onFocus` and read `adb logcat -s ReactNativeJS`; emulator screenshots can lag behind the real focus.

## Data: dev.to (Forem) API

Open source, free, no API key, and it allows requests from the browser (CORS).

- Category row: `https://dev.to/api/articles?tag=<tag>&per_page=30`
- Top stories for Home: `https://dev.to/api/articles?top=7`
- Full article (`body_html`): `https://dev.to/api/articles/<id>`

**Connection loss, recovery and timeouts.** Every dev.to request goes through `getJson` in `api/devto.ts`: a 15 s limit covers the whole request (until the body is read); a request that never answers fails as `timeout` and screens show "dev.to didn't respond. Try again in a moment." (`timedOut` on the error LoadState); a network failure is `offline` ("No connection"); an unreadable body is a plain `error`. `api/connection.ts` watches reachability: a network failure or timeout switches it to offline and it then checks dev.to every 5 s with a one-article request (webOS also checks at once on the browser's `online` event, `platform/connectivity`); any answered request switches it back online and increments `recoveries`. Hooks react with `useOnRecovery`: `useLoad` retries if it had failed, `useCachedList` retries any list not refreshed this launch, `useSearch` re-runs an offline search, and images use `useImageFailure` (a failure only counts until the next recovery). So content comes back by itself when the connection returns, without a restart or a key press; Retry buttons stay for manual retries. On Android, `MainApplication.kt` gives OkHttp a 5 s HTTP/2 ping and a 10 s connect timeout: without the ping, OkHttp keeps reusing a connection that died while offline, so every request after the network returns hangs until its timeout and recovery never happens.

**Search is custom.** dev.to's documented API has no search (its old site endpoint returns nothing; the site uses Algolia with a private-use key, which we chose not to use). Search waits 1 s after the last key, shows matches from stories already loaded at once, then fetches fresh data with the official API — the newest 100 articles (`/articles/latest`) and each query word (up to 3) as a tag — and searches again. Each fetch is reused for 2 minutes. Matching: lowercase, every query word must match the start of a word (so "rust" never matches "trusted"; in Arabic also after the "ال" prefix), title > tags > description, newest first on ties, max 40. For Arabic, remove vowel marks and treat أ/إ/آ as ا. Offline, local results are still shown with a note.

**Arabic:** translate all app text, use right-to-left layout, swap the left/right focus direction, and format dates and numbers with `Intl.*('ar')`. Use `dir="auto"` on headlines and article text: spread `{...autoDirection}` from `platform/textDirection/textDirection` onto the `Text` (adds `dir="auto"` on webOS; Android detects direction by itself). Other articles stay in English.

**Article screen.** Full screen, no menu: a fixed action column on the left (Back, Save, Next story) and the article on the right as a virtualized FlatList (`initialNumToRender` 6, `windowSize` 5), one focusable block per heading/paragraph/list item/quote/code chunk/image, so Up/Down reads block by block (centered) and Left reaches the actions from any position. The header (title, meta, cover) is the first block and gets focus first; it shows right away from `storyStore` while the body loads. Every image box is sized before it loads (cover 1000:420, body images from their width/height, else 16:9, capped at 640 design px tall), so nothing moves. Next story follows the `queue` param (ids of the row the story was opened from) and uses `replace`, so Back always returns to where the reader started.

**Home.** Top story, then 20 rows of 30 stories (checklist: 20×30, smooth, every story reachable). Story lists are cached (`api/listCache.ts`: top stories under `top`, each row under its tag, in memory and AsyncStorage as `list:<key>`, loaded once in App), so on reopen every row shows the last stories instantly, then refreshes from dev.to once per launch (`useCachedList`). Once Home is up, `prefetchLists` fetches all 20 rows in the background, 2 at a time, top first. Rows are drawn progressively: the first 4 at start, then one more every 120 ms (and focusing row N draws up to N+3 at once), so all 20 exist about 2.5 s after start and a held Down key never runs out of rows (Android moves focus natively, faster than JS can draw). An undrawn row keeps its full height (no jumps). Once a card in a row has been focused, that row keeps showing the same stories until it unmounts, so a background refresh never shifts cards under the user. Rows stay mounted once loaded so each keeps its remembered position. Each rail is a virtualized FlatList (`initialNumToRender` 6, `windowSize` 3, `getItemLayout` from the fixed card width), and card/banner images are requested at their exact pixel size (`sizedImageUrl`). Measured on the Android emulator (debug build): memory rises while the 20 rows first load, then stays flat over repeated full passes.

**Category screen.** Tabs across the top, grid below. The selected tag is screen state (not navigation), so switching tabs never adds to Back history. Focusing a tab switches the grid after 400 ms (holding Right across tabs loads nothing in between); Enter switches at once. Back while in the grid moves focus to the selected tab (`requestFocus`); Back on the tabs leaves to Home, then the exit dialog. The Back listener is registered with `useFocusEffect`, so it is only active while the screen is on top (screens under an Article stay mounted). Use the same pattern for any screen-level Back handling.

**Search screen.** Keyboard on the left (focus starts on "a"), results on the right; typing only re-renders the query text (keys are memoized), and results update 1 s after the last key. Empty query shows a hint; no results shows an empty state naming the query with tips and a "Clear search" action; while a tag is being fetched with no local results, a loading state with the same action.

**Settings and About.** Settings (in MainLayout): Text size (Small / Medium / Large / Extra large) and Language (English / العربية) as `SettingOption` rows, plus "About this app". Both settings apply at once on every screen (every size goes through the theme, and fixed heights such as card titles are computed from `lineHeight`, so layouts grow with the text). About (its own route, MainLayout current="Settings") lists app, app version, device model, OS and OS version via `AboutInfo`. Full Arabic translation and right-to-left layout are not done yet: switching to Arabic currently changes category names and dates only.

**Saved screen.** Lists saved stories (newest first) from `savedStore`. Each row: the story (Enter opens it, Next story walks the saved list) and Remove, which opens `ConfirmDialog` ("Keep" focused first; Back closes it and focus returns to Remove). After a removal the row now at that index gets `hasTVPreferredFocus`, so focus lands on the next story (or the previous one if the last was removed). The Article screen's Save button saves the whole article, then reads "Saved" (selected style); pressing it again asks to remove. A saved article opens from the saved copy, so it shows instantly and works offline. Jest mocks AsyncStorage in `jest.setup.js`.
